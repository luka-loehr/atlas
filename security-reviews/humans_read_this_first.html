SEC-20261127-001000-TM-001openmediumthreat-modelBearer token accepted in URL query string on every /v1 route including terminal, power and mutation endpoints
The global `/v1` authentication middleware (`crates/server/src/auth.rs:13-35`) accepts the master bearer token in the `?token=` query parameter for every route under `/v1`, not only read-only media playback routes. This includes high-privilege endpoints such as `GET /v1/system/terminal`, `GET /v1/system/live`, `POST /v1/system/power/{action}`, and all Photos, Drive, and Share mutation endpoints. Query-string credentials routinely leak into reverse-proxy access logs, browser history, `Referer` headers, and crash/diagnostic traces.		--confirmednot-applicableno

Additionally, line 525 computes `if pos + chunk_size + 2 > input.len()` using unchecked addition, which overflows `usize` on crafted large hex chunk sizes (panicking in debug builds and bypassing the length check to panic at slice indexing on line 528 in release builds).		--confirmednot-applicableno

SEC-20261127-004000-OPS-001openmediumoperationsdisk-guard.sh sources a mutable state file with fallback to world-writable /var/tmp
`scripts/disk-guard/disk-guard.sh:27-28,82` falls back to `STATE_DIR="/var/tmp/atlas-health"` whenever `HOME` is unset (for example in a systemd unit or CI step) and then executes `[[ -r "$STATE" ]] && source "$STATE"`. Because `/var/tmp` is world-writable and `source` executes arbitrary Bash syntax, a local unprivileged user or compromised container/service could pre-create `/var/tmp/atlas-health/disk-guard.state` and achieve command execution in the context of `disk-guard.sh`.		--confirmednot-applicableno
SEC-20261127-004001-OPS-001openmediumoperationsPostgres backup dumps lack restrictive umask and atlas-server systemd/install lack permission and hardening guards
Three operational hardening gaps affect host secret and backup confidentiality: 1. `scripts/pg-backup/backup.sh:23-39` creates `$BACKUP_DIR` and writes `atlas_*.dump` and `globals_*.sql` (containing database roles, password hashes, `api_keys` rows, and user metadata) with the process's default umask (typically `022`, making dumps world-readable). 2. `scripts/atlas/install.sh:9-12` checks that `/etc/atlas/atlas.env` exists, but does not verify or enforce mode `0600` (or `0640` owned by root/atlas) on it. 3. `scripts/atlas/atlas-server.service:7-20` sets no `UMask=0077` or baseline systemd hardening (`PrivateTmp=yes`, `ProtectKernelTunables=yes`, `ProtectKernelModules=yes`, `ProtectControlGroups=yes`), despite holding `/etc/atlas/atlas.env` secrets and running in the `docker` group.		--confirmednot-applicableno
SEC-20261127-002002-SVC-001openlowservice-pentestShare Worker putManifest buffers full body before size check and parseRange omits safe-integer check
Two defense-in-depth input-handling gaps exist in the Cloudflare Share Worker (`share/src/`): 1. `putManifest()` (`share/src/admin.ts:211-213`) reads the entire request body via `await request.text()` before checking `text.length > MAX_MANIFEST` (8 MiB), rather than rejecting oversized `Content-Length` headers upfront as `bodyLength()` does for file uploads. 2. `parseRange()` (`share/src/range.ts:21-34`) parses arbitrary-length digit sequences with `Number(startText)` / `Number(endText)` without verifying `Number.isSafeInteger(...)`, which loses precision for values above `2^53 - 1`.		--confirmednot-applicableno
