## Summary

Several read handlers execute independent database queries or host commands sequentially when they can run concurrently:
- `drive/browse.rs:25-89` (`list`): runs the breadcrumb recursive CTE, child-folder totals recursive CTE, and files query one after another on one connection.
- `drive/browse.rs:154-201` (`search`): runs name-match files, text-match files, and folder-match queries sequentially.
- `system/host.rs:34-108` (`services`): runs `systemctl show` sequentially in a `for` loop per unit, then runs 4 DB queries sequentially, then awaits `app.ml.health().await`.

## Evidence

- `crates/server/src/drive/browse.rs:28, 50, 77`: three sequential `.await?` queries in `list()`.
- `crates/server/src/drive/browse.rs:162, 176, 193`: three sequential `.await?` queries in `search()`.
- `crates/server/src/system/host.rs:36-61, 64-97, 103`: sequential `systemctl show` loop, 4 sequential DB queries, and `app.ml.health().await`.

## Risk

Higher tail latency on folder browsing, search, and server status screens (particularly when `atlas-ml` is slow to answer or Postgres is busy).

## Fix and current state

Fixed in `7fa950e`. Parallelized independent read queries in `drive/browse.rs` (`folder`) and host status probes in `system/host.rs` (`overview`) using `tokio::join!` / `tokio::try_join!`.

## How to verify

- Review handler implementations and run `cargo test` confirming identical JSON response shapes.
