## Summary

`snippet(text: &str, term: &str)` in `crates/server/src/drive/browse.rs:119-142` collects the entire extracted text of each matching Drive document into `chars: Vec<char>` and a second `lowered: Vec<char>` (8 bytes per character), then runs an O(N*M) `windows(needle.len()).position(...)` scan. `search()` (`crates/server/src/drive/browse.rs:175-191`) fetches full `df.text` (up to `CAP = 200_000` characters per file in `jobs/drive_text.rs:16`) for up to 60 matching files per request, causing up to ~96 MB of transient heap allocations and quadratic worst-case CPU work per search query.

## Evidence

- `crates/server/src/drive/browse.rs:120-129`: allocates `chars: Vec<char>` and `lowered: Vec<char>` across the entire `text` string before scanning `lowered.windows(needle.len())`.
- `crates/server/src/drive/browse.rs:175-191`: queries `SELECT ..., df.text FROM drive_files ... LIMIT 60` and calls `snippet(r.get::<_, &str>(8), term)` for every returned row.
- `crates/server/src/jobs/drive_text.rs:16`: `const CAP: usize = 200_000;`.

## Risk

Slow search latency and memory spikes on Drive libraries containing many large PDFs or text files, especially under concurrent searches.

## Fix and current state

Open. Stream or search directly on UTF-8 slices without materializing full `Vec<char>` copies (or compute the match offset in PostgreSQL using `strpos(lower(df.text), lower($2))` and fetch only a bounded `substring(df.text FROM greatest(pos - 120, 1) FOR 300)` window in SQL so full 200k-char documents never cross the DB wire during search).

## How to verify

- Keep existing `snippets_show_the_match_in_context` unit test passing, add a test with multi-byte UTF-8 characters (e.g. German umlauts / `ß`), and confirm `snippet()` no longer allocates full-text `Vec<char>` buffers.
