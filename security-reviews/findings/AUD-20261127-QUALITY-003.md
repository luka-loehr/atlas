## Summary

Multiple request handlers and background loops in `crates/server/src/` call `.lock().unwrap()` or `.read().unwrap()`/`.write().unwrap()` on `std::sync::Mutex` / `std::sync::RwLock`. If any thread panics while holding one of these locks, the lock becomes poisoned and every subsequent HTTP request or worker tick touching it will panic in a cascade.

## Evidence

- `crates/server/src/system/metrics/mod.rs:94, 177, 240`: `history.lock().unwrap()` in `latest()`, `sample_loop()`, and WebSocket `stream()`.
- `crates/server/src/photos/timeline.rs:82, 113`: `self.built.read().unwrap()` and `self.built.write().unwrap()`.
- `crates/server/src/photos/search/ml.rs:46, 72`: `self.cache.lock().unwrap()`.
- `crates/server/src/jobs/worker.rs:108, 156, 160`: `running.lock().unwrap()`.

## Risk

A single unexpected panic inside a locked critical section turns into a persistent crash loop for every caller of that subsystem until `atlas-server` is restarted.

## Fix and current state

Open. Replace `.unwrap()` on `std::sync::Mutex` / `RwLock` with `.unwrap_or_else(|e| e.into_inner())` (or switch to `parking_lot` / non-poisoning locks) where the guarded state remains valid across panics.

## How to verify

- Verify `grep -rn "\.lock()\.unwrap()\|\.read()\.unwrap()\|\.write()\.unwrap()" crates/server/src/` returns zero hits in non-test code and `cargo test` passes.
