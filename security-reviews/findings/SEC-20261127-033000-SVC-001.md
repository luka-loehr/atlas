## Summary

In the initial v0.6.0 multipart implementation (`crates/server/src/storage/multipart.rs`), `upload_dir(app, upload_id)` joined the query parameter `uploadId` directly onto `<drive_dir>/multipart` without validating that `upload_id` matched the generated `mpu_<hex>` format. In `abort_multipart`, `tokio::fs::remove_dir_all(upload_dir(app, upload_id))` was executed before checking whether `DELETE FROM multipart_uploads` matched any row (`n == 0`). An authenticated key with `write` scope on any bucket could pass `?uploadId=..%2Fblobs` to `DELETE /s3/<bucket>/<key>` and delete sibling storage directories under `drive_dir` (such as `blobs/`). Additionally, XML `POST` endpoints (`?delete` and `?uploadId=...`) did not compare an explicit 64-hex `x-amz-content-sha256` header against the read XML body bytes.

## Evidence

- `crates/server/src/storage/multipart.rs:42-44, 330-343` at `9caa842`: `app.cfg.multipart_dir().join(upload_id)` followed by `remove_dir_all` prior to `if n == 0`.
- `crates/server/src/s3/handlers.rs:248-266, 454-473` at `9caa842`: XML body read with `to_bytes` without checking optional 64-hex `x-amz-content-sha256`.

## Risk

High: any scoped API/S3 key holding `write` access to even a single isolated bucket could destroy content-addressed blobs belonging to other buckets via `AbortMultipartUpload` path traversal.

## Fix and current state

Fixed in `b62c0a7`. Added `is_valid_upload_id` (`mpu_` prefix followed by 16..64 ASCII hex digits) enforced in `upload_dir` and `list_parts`, moved `if n == 0` before `remove_dir_all` in `abort_multipart`, and added `verify_claimed_body_sha256` on S3 XML `POST` bodies in `crates/server/src/s3/handlers.rs`.
