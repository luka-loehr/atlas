## Summary

`scripts/disk-guard/disk-guard.sh:27-28,82` falls back to `STATE_DIR="/var/tmp/atlas-health"` whenever `HOME` is unset (for example in a systemd unit or CI step) and then executes `[[ -r "$STATE" ]] && source "$STATE"`. Because `/var/tmp` is world-writable and `source` executes arbitrary Bash syntax, a local unprivileged user or compromised container/service could pre-create `/var/tmp/atlas-health/disk-guard.state` and achieve command execution in the context of `disk-guard.sh`.

## Evidence

- `scripts/disk-guard/disk-guard.sh:27-28`: `STATE_DIR="${DISK_GUARD_STATE_DIR:-${HOME:-/var/tmp}/atlas-health}"` and `STATE="$STATE_DIR/disk-guard.state"`.
- `scripts/disk-guard/disk-guard.sh:82`: `[[ -r "$STATE" ]] && source "$STATE"`.

## Risk

Local privilege escalation or arbitrary code execution whenever `disk-guard.sh` runs with `HOME` unset (or if `$STATE` is tampered with), plus symlink/TOCTOU risk on `cat > "$JSON"` and `cat > "$STATE"` under `/var/tmp/atlas-health`.

## Fix and current state

Fixed in `410e5de`. Replaced bash `source "$STATE_FILE"` in `scripts/disk-guard/disk-guard.sh` with a strict line-by-line `LAST_LEVEL`/`LAST_EPOCH` parser (no command execution) and removed the world-writable `/var/tmp` fallback in favor of `0700` `$HOME/.local/state/atlas`.

## How to verify

- Confirm `scripts/disk-guard/disk-guard.sh` contains no `source` of `$STATE` and does not fall back to a shared `/var/tmp/atlas-health` directory; test with a synthetic state file containing shell metacharacters and verify no command is executed.
