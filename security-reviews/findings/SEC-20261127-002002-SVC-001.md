## Summary

Two defense-in-depth input-handling gaps exist in the Cloudflare Share Worker (`share/src/`):
1. `putManifest()` (`share/src/admin.ts:211-213`) reads the entire request body via `await request.text()` before checking `text.length > MAX_MANIFEST` (8 MiB), rather than rejecting oversized `Content-Length` headers upfront as `bodyLength()` does for file uploads.
2. `parseRange()` (`share/src/range.ts:21-34`) parses arbitrary-length digit sequences with `Number(startText)` / `Number(endText)` without verifying `Number.isSafeInteger(...)`, which loses precision for values above `2^53 - 1`.

## Evidence

- `share/src/admin.ts:211-213`: `const text = await request.text(); if (text.length > MAX_MANIFEST) return error(413, "manifest too large");`
- `share/src/range.ts:23,29,31`: `Number(endText)` and `Number(startText)` accept arbitrarily many digits without checking `Number.isSafeInteger`.

## Risk

Low: `putManifest` is behind `SHARE_TOKEN` admin auth and Cloudflare Workers enforce a 100 MB body limit; `parseRange` operates on public `Range` headers where values >= `size` return `"unsatisfiable"`, so precision loss mainly affects edge-case handling near `Infinity` or `Number.MAX_SAFE_INTEGER`. Tightening both keeps memory and RFC 9110 range behavior predictable.

## Fix and current state

Fixed in `410e5de`. Added pre-read `Content-Length > MAX_MANIFEST` rejection and streaming byte-budget reader in `share/src/admin.ts`, plus `Number.isSafeInteger` checks in `share/src/range.ts`.

## How to verify

- Add unit tests in `share/test/units.test.ts` and `share/test/worker.test.ts` covering oversized `Content-Length` on `PUT /api/shares/{id}` and huge `Range: bytes=99999999999999999999-` headers.
