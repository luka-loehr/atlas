## Summary

The CLI (`crates/cli/src/`) passes `ssh_host()` (from `ATLAS_SSH_HOST` or `~/.config/atlas/env`) directly to `Command::new("ssh")` without validating against a leading `-` or passing `--`, and `crates/cli/src/exec.rs:153-168` interpolates `{wd}`, `{tag}`, and `$envf` into a remote shell string without single-quoting. Additionally, `crates/cli/src/config.rs:138-163` reads `~/.config/atlas/env` without warning if it is group/world-readable.

## Evidence

- `crates/cli/src/ssh.rs:22-26, 88-104`: `Command::new("ssh").args([ssh_host(), remote])` has no `--` before `ssh_host()` and `Config::load()` (`crates/cli/src/config.rs:103`) does not reject `ATLAS_SSH_HOST` values starting with `-`.
- `crates/cli/src/exec.rs:154-166`: `docker run --rm --network host $envf ... -w {wd} {tag} sh -c {cmd}` leaves `$envf` and `{wd}` unquoted in the remote shell.
- `crates/cli/src/secrets.rs:109-115`: `envf="--env-file $sec"` relies on word-splitting when expanded unquoted in `exec.rs:154`; if `$HOME` or a project path ever contains whitespace or glob characters, `$envf` breaks or splits unexpectedly.

## Risk

Low in normal single-user operation, but an `ATLAS_SSH_HOST` starting with `-` is interpreted as an `ssh` option (e.g. `-oProxyCommand=...`), and unquoted remote shell expansions in `exec.rs` / `secrets.rs` are fragile against spaces or shell metacharacters in `atlas.toml` fields.

## Fix and current state

Open. Validate `ATLAS_SSH_HOST` in `Config::load()` (non-empty, must not start with `-`, no whitespace/control chars) and pass `"--"` before `ssh_host()` in `ssh.rs` / `deploy.rs` / `exec.rs` / `secrets.rs`. Quote `{wd}` and `{tag}` with `shq(...)` and pass `--env-file "$sec"` conditionally without unquoted `$envf` word-splitting.

## How to verify

- Add unit tests in `crates/cli/src/config.rs` verifying `ATLAS_SSH_HOST` values starting with `-` are rejected, and verify `cargo test -p atlas-cli` passes.
