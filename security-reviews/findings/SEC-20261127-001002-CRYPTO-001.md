## Summary

`decode_aws_chunked_bytes()` in `crates/common/src/s3.rs:508-535` decodes `STREAMING-AWS4-HMAC-SHA256-PAYLOAD` (`aws-chunked`) request bodies by splitting each chunk header on `;` and discarding `;chunk-signature=...` without verifying the chained HMAC-SHA256 chunk signatures. Additionally, line 525 computes `if pos + chunk_size + 2 > input.len()` using unchecked addition, which overflows `usize` on crafted large hex chunk sizes (panicking in debug builds and bypassing the length check to panic at slice indexing on line 528 in release builds).

## Evidence

- `crates/common/src/s3.rs:518`: `let size_hex = header_line.split(';').next().unwrap_or("").trim();` ignores the `chunk-signature=` extension completely.
- `crates/common/src/s3.rs:525-528`: `if pos + chunk_size + 2 > input.len()` uses unchecked `usize` addition before `&input[pos..pos + chunk_size]`.
- `crates/common/src/s3.rs:638-641`: unit test `decodes_aws_chunked_payload` passes placeholder signatures (`aaaa`, `bbbb`, `cccc`) and succeeds.

## Risk

Once wired into an S3 server upload path, a caller or MITM on plain HTTP can tamper with chunk payloads without failing SigV4 chunk-signature verification, and a crafted chunk header with a huge hex size (e.g. near `usize::MAX`) can trigger a release-mode slice panic (DoS) in the decoder.

## Fix and current state

Open. Replace `pos + chunk_size + 2` with `pos.checked_add(chunk_size).and_then(|n| n.checked_add(2))` returning `Err(SigV4Error::ChunkFramingError)` on overflow, and either verify chained SigV4 chunk signatures (`AWS4-HMAC-SHA256-PAYLOAD`) against the seed signature and signing key or document/restrict `decode_aws_chunked_bytes` to unsigned streaming payloads only.

## How to verify

- Add a unit test in `crates/common/src/s3.rs` passing `ffffffffffffffff\r\nabc\r\n` to `decode_aws_chunked_bytes` and asserting `Err(SigV4Error::ChunkFramingError)` without panicking.
- Verify that signed streaming chunks with invalid `chunk-signature` values are rejected.
